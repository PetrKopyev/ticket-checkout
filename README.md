# Билеты и уведомления организатора

Тестовое задание Sqoch в одном проекте: **Тест 1** — интерфейс покупки билетов на моковых данных,
**Тест 2** — помощник и рассылка покупателям о переносе мероприятия (API и кабинет организатора).
React 19 + TypeScript + Vite + Tailwind 4, тесты на Vitest; сервер Теста 2 — Node без фреймворков, база SQLite.

## Запуск

```
npm ci
npm run dev      # http://localhost:5173 (билеты), кабинет: http://localhost:5173/#/organizer; API работает внутри Vite
npm run api      # отдельный API-сервер на 127.0.0.1:3001 (раздаёт и собранный dist/)
npm start        # npm run build, затем npm run api
npm test         # правила, мок-API, получатели, рассылка, API, помощник, клиент кабинета
npm run build    # проверка типов и сборка
npm run lint     # oxlint
```

Нужен Node 22.18+: с этой версии `node server/main.ts` запускается без флагов. Сервер использует `node:sqlite`,
он помечен экспериментальным, поэтому предупреждение в консоли при старте — это нормально.

Переменные окружения (все необязательные):

| Переменная | По умолчанию | Что делает |
| --- | --- | --- |
| `DB_PATH` | `data/app.db` | файл базы SQLite (создаётся и наполняется демо-данными при первом старте) |
| `PORT` | `3001` | порт `npm run api` |
| `MAIL_DELAY_MS` | `400` | максимальная пауза перед письмом; фактическая — `min(MAIL_DELAY_MS, 8000 / число получателей рассылки)` мс: для 6 адресов 400 мс, для 1000 — 8 мс; `0` отключает паузу |
| `LLM_BASE_URL` | `https://api.openai.com/v1` | адрес OpenAI-совместимого API |
| `LLM_MODEL` | `gpt-4o-mini` | модель |
| `LLM_API_KEY` | нет | ключ OpenAI-совместимого API; обязателен при `LLM_PROVIDER=openai` |
| `GIGACHAT_AUTH_KEY` | нет | ключ авторизации GigaChat в base64; обязателен при `LLM_PROVIDER=gigachat` |
| `GIGACHAT_SCOPE` | `GIGACHAT_API_PERS` | scope для OAuth GigaChat |
| `GIGACHAT_MODEL` | `GigaChat` | модель GigaChat |
| `LLM_PROVIDER` | авто | `gigachat`, `openai` или `fake`; регистр и пробелы по краям не важны; явный выбор имеет приоритет над ключами |

Без ключей и явного выбора провайдера используется детерминированная имитация LLM (тот же цикл с инструментами):
она понимает название мероприятия в кавычках и дату вида «на 20 ноября, 19:00», на остальное просит уточнить.
Для OpenAI-совместимого API задайте `LLM_API_KEY`, при необходимости — `LLM_BASE_URL` и `LLM_MODEL`.

### GigaChat

В личном кабинете [developers.sber.ru](https://developers.sber.ru/) создайте проект GigaChat API.
В разделе «Авторизационные данные» возьмите ключ в base64 для `GIGACHAT_AUTH_KEY`.

Непустой `LLM_PROVIDER` выбирает ровно указанный провайдер; неизвестное значение или отсутствие
ключа для выбранного GigaChat/OpenAI останавливает запуск с ошибкой. Без явного выбора:
`GIGACHAT_AUTH_KEY` → GigaChat, иначе `LLM_API_KEY` → OpenAI-совместимый API, иначе имитация.

Сертификаты НУЦ Минцифры лежат в `certs/russian_trusted_root_ca.cer` и `certs/russian_trusted_sub_ca.cer`.
Источники: [корневой сертификат](https://gu-st.ru/content/Other/doc/russian_trusted_root_ca.cer),
[промежуточный сертификат](https://gu-st.ru/content/Other/doc/russian_trusted_sub_ca.cer),
[информация об установке](https://www.gosuslugi.ru/crt).
Срок действия сертификата sub CA — до 06.03.2027.
Клиент добавляет их к стандартным доверенным сертификатам Node при первом HTTPS-запросе; проверка TLS включена.

Запуск:

```sh
read -s GIGACHAT_AUTH_KEY; export GIGACHAT_AUTH_KEY; npm run api
```

## Как это устроено

### Тест 1 — билеты

Три шага: участники → проверка → результат. Успешный результат оформлен как билет с номером заказа,
QR-кодом (`qrcode.react`) и событием; «Скачать билеты» открывает печать браузера
(там же «Сохранить как PDF»), на бумаге остаётся только билет.

- `src/rules.ts` — чистые функции цены, итога, валидации участника, email и заказа;
  `buildOrder` обрезает пробелы по краям имени и email, схлопывает пробелы в имени
  и делает первую букву заглавной.
- `src/api.mock.ts` — 10 моковых мест и `confirmOrder` с задержкой 400 мс;
  места перепроверяются в момент подтверждения.
- `src/event.ts`, `src/format.ts`, `src/types.ts` — событие, форматирование цены, возраста и мест, типы.
- `src/App.tsx` — состояние заказа, шаги, фокус на заголовке и переключение между билетами и кабинетом (хеш `#/organizer`).
- `src/components/` — `EventHeader`, `StepIndicator`, `ParticipantsStep`, `ParticipantCard`, `ReviewStep`,
  `ResultStep`, `OrderSummary`, `SubmitBar` (закреплённая мобильная панель), `CheckIcon`, `ui.ts` (общие классы).
- `src/index.css` — токены темы, отступ под закреплённую панель, стили печати билета.

Правила из задания:

- Полный билет 2000 ₽ (от 14 лет), детский 1000 ₽ (младше 14).
- От 1 до 4 участников; у каждого имя и возраст, один email на заказ.
- Ребёнок младше 14 допускается только с участником от 18 лет в том же заказе.
  Участник 14–17 лет платит полный билет, но сопровождающим не считается.

### Тест 2 — кабинет организатора и рассылка

Организатор пишет помощнику «Переносим мастер-класс "Керамика" на 20 ноября, 19:00. Подготовь уведомление покупателям».
Помощник через инструменты находит мероприятие, считает получателей и создаёт **черновик**. Организатор видит
мероприятие, текст и список получателей, правит их, явно подтверждает отправку и следит за прогрессом по каждому адресу.

Карта файлов сервера (`server/`):

- `main.ts` — HTTP-сервер `npm run api`: только `127.0.0.1`, проверка `Host`, раздача `dist/`, заголовки безопасности.
- `vitePlugin.ts` — подключает тот же API к `vite` (dev и preview); в тестах отключён.
- `app.ts` — сборка приложения: база, демо-данные, почтовая служба, выбор LLM, `recoverCampaigns` при старте.
- `api.ts` — маршруты, проверки запроса, коды ошибок.
- `db.ts` — схема SQLite и `transaction`.
- `recipients.ts` — **правила получателей**.
- `campaigns.ts` — черновик, подтверждение, отправка, продолжение, восстановление.
- `mailer.ts` — «почтовая служба»: запись в `outbox` вместе с ключом идемпотентности `campaignId:email`, флаг недоступности для демо.
- `seed.ts` — два мероприятия и 20 покупок; `createBigDemo` и `resetDemo`.
- `env.ts` — разбор `PORT` и `MAIL_DELAY_MS` с понятными ошибками.
- `static.ts` — путь к файлу из `dist` или `index.html` для маршрутов SPA.
- `llm/date.ts` — разбор дат и времени переноса в тексте; `llm/limit.ts` — чтение ответа LLM с лимитом 1 МБ.
- `llm/` — `assistant.ts` (цикл диалога и история), `tools.ts` (инструменты), `openai.ts` и `gigachat.ts` (клиенты),
  `select.ts` (выбор провайдера), `fake.ts` (имитация без ключа), `types.ts`.

Кабинет (`src/organizer/`): `Organizer` (страница), `ChatPanel` (чат), `CampaignList` (список рассылок),
`CampaignPanel` (мероприятие, письмо, счётчики, прогресс, подтверждение и «Повторить»), `RecipientsDialog`, `EmailPreview`, `ConfirmDialog`,
`OutboxList` (последние 3 отправленных письма и общее число), `DemoPanel` (демо-настройки), `client.ts` (запросы к API),
`validate.ts`, `status.ts`, `recipientsList.ts` (слияние страниц, исключения, вкладки и доступность досылки).

Над панелью расположен блок «Рассылки»: последние пять, новые сверху, с темой, статусом и прогрессом.
«Показать все (N)» раскрывает остальные; выбор открывает рассылку в панели. После перезагрузки открывается
последняя, после создания черновика помощником — созданная рассылка.

Кнопка «Получатели (N)» открывает окно с поиском по почте, вкладками со счётчиками и догрузкой по 20 адресов
при прокрутке внутри окна. Поиск применяется к выбранной вкладке. В черновике доступны «Все» и «Исключены»;
чекбоксы сразу сохраняют исключения, не затрагивая несохранённые правки письма. После подтверждения доступны
также «Отправлено», «Ожидают» и «Ошибки». Из завершённой рассылки можно дослать исключённому адресу или всем
исключённым через подтверждение. Escape и «Закрыть» возвращают фокус на кнопку открытия.
Общее число адресов включает исключённых (`total + excluded`); предпросмотр, подтверждение и прогресс
используют число адресов без исключённых (`total`). Опрос отправки раз в секунду загружает рассылку без адресов;
открытое окно само список не опрашивает.

Схема SQLite:

- `events` — мероприятие (id, название, дата, место);
- `purchases` — покупка (мероприятие, покупатель, email, статус `active`/`cancelled`, число билетов);
- `campaigns` — рассылка: тема, текст, статус `draft` → `sending` → `completed` или `partial`
  (из `partial` обратно в `sending` — только «Повторить», из `completed` — только досылка исключённому);
- `deliveries` — получатель рассылки, ключ `(campaign_id, email)`: статус `pending`/`sent`/`failed`, число попыток,
  ошибка, признак исключения организатором;
- `outbox` — «отправленные» письма, `UNIQUE (campaign_id, email)` и `idempotency_key UNIQUE`;
- `chat_messages` — история диалога с помощником (включая вызовы инструментов);
- `settings` — флаг `mailer_down` демо.

HTTP API (ошибки приходят как `{ "error": "..." }`):

| Метод и путь | Что делает |
| --- | --- |
| `GET /api/events` | мероприятия |
| `GET /api/limits` | пределы длины письма: `{ subject, body }` (200 и 5000) |
| `GET /api/assistant/history` | история чата |
| `POST /api/assistant/message` | сообщение помощнику `{ text }`, ответ — `{ reply, campaignId }` |
| `GET /api/campaigns` | список рассылок |
| `GET /api/campaigns/:id` | рассылка без массива `recipients`: счётчики `total`, `sent`, `failed`, `pending` среди не исключённых, число `excluded` и отсортированный по email список `excludedEmails` |
| `GET /api/campaigns/:id/recipients` | параметры `tab=all\|sent\|pending\|failed\|excluded` (по умолчанию `all`), `q` (подстрока email, без учёта регистра, пробелы по краям убираются, до 320 символов, `%`, `_` и `\` — обычные символы), `offset=0`, `limit=20` (1–100); ответ `{ items: [{ email, status, error, excluded }], total, counts: { all, sent, pending, failed, excluded } }`, порядок по email; `total` учитывает вкладку и поиск, `counts` — всю рассылку без поиска; `all` включает исключённых, вкладки статусов — только не исключённых |
| `PATCH /api/campaigns/:id` | правка черновика: `subject`, `body`, `excluded` (список email не длиннее общего числа получателей, иначе `400`); `409`, когда рассылка уже подтверждена |
| `POST /api/campaigns/:id/confirm` | обязательное тело `{ subject, body, excluded: string[] }` из окна подтверждения; `409` при расхождении с сохранённым содержимым, в том числе у уже отправленной рассылки; запуск отправки в фоне, ответ — рассылка; повтор с совпадающим содержимым даёт `200` без повторной отправки |
| `POST /api/campaigns/:id/resume` | продолжение рассылки в статусе `partial` |
| `POST /api/campaigns/:id/include` | дослать исключённому `{ email }` после отправки (`completed`), ответ — рассылка |
| `POST /api/campaigns/:id/include-all` | тело `{}`; включить и дослать всем исключённым из `completed`, ответ — рассылка; `409` при другом статусе или отсутствии исключённых |
| `GET /api/outbox` | последние 3 отправленных письма и общее число: { items, total } |
| `POST /api/demo/big` | тело `{}`; большое демо, ответ `{ campaignId, recipients: 860 }`; повторный вызов возвращает существующий черновик festival и не дублирует покупки |
| `GET /api/demo`, `POST /api/demo/mailer` `{ down }`, `POST /api/demo/reset` | демо: служба отправки и сброс данных |

GET/PATCH/confirm/resume/include/include-all возвращают рассылку без массива `recipients`.
`offset` и `limit` принимают только десятичные целые по шаблону `^\d+$`, `offset` неотрицательный.

Коды ошибок: `400` — неверное тело или параметры вкладки, поиска и пагинации, слишком длинный список исключений, пустая или слишком длинная тема/текст (до 200 и 5000 символов), сообщение помощнику
до 2000 символов; `403` — `Origin` не совпадает с `Host` (в `main.ts` ещё и чужой `Host`); `404` — нет рассылки, получателя или пути;
`409` — PATCH уже подтверждённой рассылки, расхождение подтверждаемого письма с сохранённым содержимым, в том числе у уже отправленной рассылки, нет получателей, пустое письмо, помощник занят, досылка в черновике, во время
отправки, в `partial` или получателю, который не исключён, а также `include-all` без исключённых; `413` — тело больше 256 КБ;
`415` — не `application/json`; `502` — помощник (LLM) недоступен; `500` — прочие сбои.

**Получатели** — email с хотя бы одной действующей (`active`) покупкой выбранного мероприятия; email приводится
к нижнему регистру и без пробелов по краям, на адрес одно уведомление. Отменённые покупки не учитываются, адрес
только с отменёнными покупками не попадает в список. Менять правило нужно в `server/recipients.ts`.

**Помощник и граница LLM.** Инструменты: `list_events`, `get_event`, `list_recipients` (только количество),
`create_draft_campaign`. У LLM нет инструмента отправки и подтверждения: отправка идёт только из
`POST /confirm`, который вызывает организатор в интерфейсе. За один ответ создаётся не больше одного черновика,
цикл ограничен 6 шагами, результаты инструментов в системной подсказке названы данными, а не инструкциями.
LLM видит число получателей, но не адреса. Получателей черновика выбирает код, не модель.
GigaChat получает только первый вызов инструмента из каждой реплики и возвращает максимум один вызов за шаг;
результаты инструментов передаются как сообщения `function` с именем вызова.

**Идемпотентность и надёжность.**

- `confirm` меняет статус одним `UPDATE ... WHERE status = 'draft'`; повторное подтверждение ничего не запускает и
  не создаёт писем.
- `deliveries` с первичным ключом `(campaign_id, email)` и `outbox` с `UNIQUE (campaign_id, email)` и `UNIQUE (idempotency_key)` не дают создать второе
  письмо на адрес даже при гонке; `activeSends` не допускает двух одновременных циклов отправки одной рассылки.
- Отправка идёт по одному адресу и сразу фиксирует результат. Если служба недоступна, текущий адрес получает `failed`,
  цикл останавливается, рассылка становится `partial`. «Повторить» (`resume`) шлёт только `pending` и `failed`,
  уже `sent` не трогает.
- Данные лежат в SQLite (WAL): закрытие страницы ничего не меняет, а при перезапуске сервера `recoverCampaigns`
  дошлёт рассылки, которые остались в статусе `sending`.

## Как показать сценарий

Показ сбоя службы отправки (пошагово):

1. `npm run dev` (или `npm run api` после `npm run build`), открыть `#/organizer`. Для наглядности можно поднять
   `MAIL_DELAY_MS=1500`.
2. В «Демо-настройки» нажать «Сбросить данные», затем выбрать «Служба отправки: Недоступна».
3. Написать помощнику: «Переносим мастер-класс "Керамика" на 20 ноября, 19:00. Подготовь уведомление покупателям»,
   нажать «Открыть черновик»: видны тема, текст и 6 получателей. Можно поправить текст и исключить адрес.
4. «Подтвердить и отправить» → подтвердить в диалоге. Первый адрес получает `failed` («Служба отправки недоступна»), остальные
   остаются `pending`, рассылка остановлена: статус «Не отправлена» (если ушло 0 писем) или «Отправлена частично».
5. Переключить службу на «Работает», нажать «Повторить отправку (N)»: письма уйдут только тем, кто ещё не получил;
   список «отправленные письма» не содержит дублей.
6. Повторное подтверждение (в том числе повторный запрос `POST /confirm`) новых писем не создаёт.

Перезапуск посередине:

1. `MAIL_DELAY_MS=3000 npm start` (соберёт `dist` и запустит сервер; позже достаточно `npm run api`), на `http://127.0.0.1:3001/#/organizer` создать и подтвердить рассылку.
2. Пока идёт отправка, остановить процесс (Ctrl+C или `kill` по PID) и запустить `npm run api` снова.
3. После старта `recoverCampaigns` дошлёт оставшихся: уже отправленные не повторяются. Страницу можно закрыть и открыть заново,
   рассылка и её состояние на месте (в списке рассылок и в «отправленных письмах»).
4. Если процесс остановился в момент ошибки и рассылка осталась в `partial`, сама она не продолжится — нажмите «Повторить».

Большое демо: кнопка «Демо: рассылка на 1000 получателей» в «Демо-настройках» открывает созданный черновик.
Она вызывает `POST /api/demo/big` с JSON-телом `{}`, который создаёт «Фестиваль "Большой город"»
(5 декабря 2026, 18:00, Москва) и черновик переноса на 12 декабря, 18:00.
В 1000 покупках: 860 уникальных активных адресов, 60 активных дублей с другим регистром и пробелами,
40 отменённых покупок адресов с активными покупками и 40 адресов только с отменами.
После нормализации получается 860 получателей. `campaignId` из ответа можно использовать для пагинации,
PATCH исключений и confirm; тему, текст и исключения для confirm берите из GET рассылки.
Повторный вызов возвращает существующий черновик; после подтверждения создаёт новый без дублирования покупок.
При стандартном `MAIL_DELAY_MS=400` пауза для 860 адресов составляет около 9,3 мс на письмо.

«Сбросить данные» возвращает исходные два мероприятия и 20 покупок, стирает рассылки, письма и историю чата и включает службу.
Мероприятие festival и его покупки также удаляются; после сброса `/api/demo/big` снова создаёт большое демо.

Показ «места закончились» из Теста 1: внизу страницы билетов есть демо-панель. Заполните заказ до шага «Проверьте заказ»,
нажмите «Демо: кто-то купил билеты» (мест станет 0) или «Демо: осталось 1 место» (в заказе 2 и больше участников),
затем «Подтвердить»; «Сбросить демо» возвращает 10 мест.

## Допущения и решения

- «Повторить отправку» намеренно без второго окна подтверждения: рассылка уже подтверждена организатором, повтор лишь дошлёт неотправленные.
- Один процесс на одну базу данных: если запустить два сервера на одном `data/app.db` (например, `npm run dev` и `npm run api`),
  второй при старте подхватит рассылки в статусе `sending` и начнёт слать. Для второго экземпляра задайте свой `DB_PATH`.
- Несохранённые правки черновика пропадают при закрытии вкладки; после «Сохранить» они в базе.
- Для уже подтверждённой рассылки (не `draft`) повторный `POST /confirm` с совпадающим содержимым отвечает `200` без повторной отправки; другое содержимое возвращает `409`.
- На сервере нет лимитов на длину истории чата — только локальный запуск.
- Получатели фиксируются при создании черновика: покупки, появившиеся позже, в эту рассылку не попадут.
- После отправки исключённого можно вернуть (`POST /include`): ему уходит ровно одно письмо с тем же ключом
  `campaignId:email`, остальным ничего не повторяется. Возвращать можно по одному (`POST /include`) или всех сразу (`POST /include-all`), только из `completed`.
  В `partial` сначала нужно нажать «Повторить»; досылка из `draft`, `sending` и `partial` возвращает `409`.
- Рассылка в `partial` после рестарта не дослается сама: нужна кнопка «Повторить» (автоматически продолжаются только `sending`).
- Письма пишутся в таблицу `outbox`: SMTP нет. Для настоящего SMTP ключ `campaignId:email` нужно передавать провайдеру как ключ идемпотентности, иначе доставка
  «хотя бы один раз» (at-least-once): при падении между отправкой и записью `sent` письмо может уйти повторно.
- Кабинет без авторизации. Защита: запись только `application/json`, проверка `Origin` и `Host`, сервер слушает
  только `127.0.0.1`, лимиты размера тела (256 КБ) и текстов.
- Схема без миграций: после правки схемы удалить `data/` (в частности, после обновления с версии без `idempotency_key` в `outbox`).
- В шапке рассылки и в окне подтверждения дата события подписана «Дата в афише сейчас: …»: это текущая дата в афише, новая дата указана в письме.
- Если нажать «Сбросить данные» ровно в паузу между письмами, в `outbox` может остаться одно письмо удалённой рассылки; в интерфейсе оно не видно (демо-ограничение).
- LLM получает только количество получателей, не адреса.
- Реализованы OpenAI-совместимый провайдер (`server/llm/openai.ts`) и GigaChat (`server/llm/gigachat.ts`), таймаут 30 с на каждый запрос (OAuth и chat отдельно).
  GigaChat проверяется на локальном HTTP-сервере: OAuth, кеш токена, инструменты и ошибки. Внешние API в тестах не вызываются.
- Тест 1: число детей на одного взрослого не ограничено (в задании нет); возраст — целое от 0 до 120; имя до 60 символов;
  одинаковые имена допустимы (тёзки); email проверяется шаблоном и ограничен 254 символами. Мок проверяет только места,
  настоящий бэкенд должен повторять правила из `rules.ts`.

## Время и незавершённое

**Тест 1.** Фактическое время: около 2,5 часов (по истории коммитов 22.10, 13:55–16:30). Сверх сценария из ТЗ сделаны:
оформление в стиле sqoch.com, индикатор шагов, закреплённая панель на телефоне, QR и печать билета,
а также ревью и проверки интерфейса на ширинах 320–1280.

Не сделано в Тесте 1:

- реального бэкенда, оплаты и отправки письма нет, это моки;
- состояние не сохраняется между перезагрузками;
- кнопка браузера «Назад» уходит со страницы (нет роутера и истории шагов).

**Тест 2.** Фактическое время: около 6 часов: 1,5 часа основной работы (26.10 с 23:49 до 27.10 01:15, от согласования плана до первых видео) и около 4,5 часа доработки 27.10 (с 08:55 до 13:30: подключение GigaChat, окно получателей с поиском и подгрузкой, список рассылок, демо на 1000 получателей, правки по замечаниям ревью, повторные проверки).
Видео процесса и короткая демонстрация результата: _добавить ссылки_.

Не сделано в Тесте 2:

- настоящего SMTP нет: письма попадают только в `outbox`;
- авторизации организатора нет;
- реальный вызов внешнего LLM не входит в сдаваемые проверки (имитация, подставные клиенты и локальный сервер GigaChat);
- кнопка «Открыть черновик» в чате не восстанавливается из истории после перезагрузки страницы (черновик остаётся в списке рассылок);
- миграций схемы нет.
